## 1. Принципы серии

1. Это проект <b>чисто для Codex</b>, не учебное упражнение. Пользователь не пишет код.
2. <b>Один этап = один вертикальный результат</b>: рабочий запуск, тесты, изменения в документации. Не выпускать пустые интерфейсы вместо функционирующей модели.
3. <b>Сохранять существующее:</b> перед началом каждого этапа прочитать [AGENTS.md](http://AGENTS.md), [ARCHITECTURE.md](http://ARCHITECTURE.md), [ROADMAP.md](http://ROADMAP.md), состояние git; не переписывать всё без объективной причины.
4. <b>Не ожидать бесконечной автономности:</b> задача конечная и должна остановиться с отчётом, если завершена или требует доступа. Не тратить лимиты ради траты лимитов.
5. <b>Нет фантазий про тесты:</b> если проверка не запускалась, отметить NOT RUN и причину; приложить реальные результаты.
6. <b>Технический документ - ориентир:</b> архитектурное отклонение допустимо лишь с ADR, тестами и причиной.
7. <b>Без опасных действий:</b> никаких публичных деплоев, покупок, удаления пользовательских данных, внешних секретов или изменений за пределами репозитория.
8. <b>Единственная обязательная ручная работа пользователя:</b> при необходимости открыть интерфейс и прислать 1–2 скриншота; остальное должен сделать Codex.

## 2. Проверочный протокол, обязательный после КАЖДОГО этапа

Codex должен автоматически выполнять все доступные проверки, соответствующие затронутому коду, а в конце ответа вывести <b>один отчёт в следующем формате</b>:

```txt
DIGITAL DARWIN — MILESTONE REPORT
STAGE: DD-XX
STATUS: PASS | PARTIAL | FAIL | BLOCKED
COMMIT: <git sha или UNCOMMITTED>
BUILD: <точная команда> -> PASS/FAIL/NOT RUN
TYPECHECK: <точная команда> -> PASS/FAIL/NOT RUN
LINT: <точная команда> -> PASS/FAIL/NOT RUN
UNIT: <команда> -> PASS/FAIL/NOT RUN, N passed, M failed
INTEGRATION: <команда> -> PASS/FAIL/NOT RUN
E2E: <команда> -> PASS/FAIL/NOT RUN
LONG_RUN: <seed/config/ticks> -> PASS/FAIL/NOT RUN
PERFORMANCE: <N agents, map size, runtime, TPS p50/p95, RAM> или NOT RUN
DETERMINISM: <seed/ticks/hashA/hashB> -> PASS/FAIL/NOT RUN
WHAT_CHANGED:
  - ...
EVIDENCE:
  - <путь к отчёту/скриншоту/логу>
LIMITATIONS:
  - ...
BREAKING_CHANGES: none | ...
BLOCKERS:
  - ...
NEXT_RECOMMENDED_STAGE: DD-XX
END MILESTONE REPORT
```

<b>Важно:</b> сохранить развёрнутую копию в <code>reports/DD-XX.md</code> и компактную структуру в <code>reports/latest.json</code> с кодами результата. Ссылки на evidence - реальные пути в репозитории, не выдуманные. Для любых изменённых функций:

- <code>pnpm lint</code> и <code>pnpm typecheck</code> (если команды настроены);
- <code>pnpm test</code> на все unit/integration;
- <code>pnpm build</code>;
- <code>pnpm test:e2e</code> для UI, если Playwright и браузер доступны;
- минимум один воспроизводимый headless run; <code>determinism</code> при изменении движка;
- отдельная проверка бюджета ресурсов / численности / ненулевых ресурсов, когда применимо.

<b>Решение о следующем этапе принимаю я после получения отчёта.</b> Codex не должен самовольно переходить к следующим этапам в рамках текущего запроса. Если в отчёте FAIL/NOT RUN у критичного теста, следующий запрос будет исправляющим.

## 5. Шаблон исправляющего запроса DD-FIX

Если я отвечаю <b>FIX</b>, вместо следующего этапа запускается этот шаблон с конкретным отчётом:

```txt
STAGE DD-FIX-XX — REGRESSION REPAIR

Твой предыдущий milestone: <DD-XX>.
Ниже фактический отчёт проверок / ошибки:
<ВСТАВИТЬ РЕЗУЛЬТАТ>

Работай только над причиной обнаруженной проблемы и её
прямыми последствиями. Сначала воспроизведи дефект,
затем добавь тест, который падает на старой версии
и проходит после исправления. Исправь root cause,
не подавляй тесты, не меняй ожидаемые значения без ADR
или честного объяснения. Выполни повторно проверку
предыдущего этапа, общую регрессию и воспроизводимый
headless run. Выдай обновлённый MILESTONE REPORT.
Не переходи к следующему функциональному этапу.
```

## 6. Что пользователь присылает после каждого запуска

Просто скопируй <b>MILESTONE REPORT</b> из ответа Codex. Если есть падения, желательно добавь stderr/логи, на которые он ссылается. Для UI-этапов иногда нужен один скриншот; большую кодовую базу или весь diff каждый раз присылать не надо. Если отчёт сомнительный или не содержит фактических команд, мы вернём его на уточнение.

<b>Мой порядок ревью:</b>

1. Проверка соответствия поставленному этапу.
2. Поиск несоответствий в числах, командах, seed/state hash и «успешных» тестах без evidence.
3. Проверка, что нет breaking changes старых функций/сохранений.
4. Решение <b>PASS</b> (следующий этап), <b>FIX</b> (исправление/допроверка), <b>BLOCKED</b> (нужен доступ/контекст).
5. Формирование точного промпта следующего шага, скорректированного по полученному отчёту.
